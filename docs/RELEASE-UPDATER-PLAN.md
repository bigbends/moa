# 릴리스와 업데이트 체계 계획

작성: 2026-10-08. 상태: 설계 제안. 이 문서 작성은 릴리스 발행·배포·자동 업데이트 활성화를 의미하지 않는다.

## 목표

일반 사용자는 Git이나 로컬 빌드 없이 설치하고, 설정 화면에서 정식/베타 채널과 새 버전을 확인한다. 원할 때 즉시 적용하거나 원하는 시간에 자동 적용한다. 개발자는 기존 Git 작업을 계속할 수 있다. 이미지·설치 파일·업데이터를 버전 단위로 관리하고, 업데이트 실패가 설치 전체를 망가뜨리지 않도록 한다.

초기 지원 대상은 Linux Docker Compose 설치다. 개발용 Git 설치의 기존 확인/수동 적용은 유지하되 릴리스 자동 적용 대상에서는 제외한다. 별도 업데이트 서버와 별도 공개 저장소는 만들지 않는다. 기존 GitHub Releases, GHCR, 호스트 업데이트 도구를 활용한다.

## 현재 구현에서 바꿔야 하는 점

- `.github/workflows/images.yml`: main마다 latest, v* 태그별 이미지 발행. 브라우저 서비스는 이미지 행렬에서 빠져 있다.
- `scripts/update.mjs`: Docker 모드여도 Git 폴더이면 source()를 선택해 추적 브랜치를 갱신하고 로컬 빌드한다. 이미지 설치는 check 중에도 pull한다.
- 이미지 갱신 대상은 moa/auth/apk/connector만 포함한다. 활성화한 브라우저 서비스가 빠진다.
- serve는 시작할 때 한 번 확인하고 웹 요청을 처리한다. 정기 확인/자동 적용/유지보수 시간은 없다.
- 상태는 커밋·이미지 ID 위주이고 적용 단계, 재시작 복구, 설치 이력이 부족하다.
- `apps/server/src/updates.ts`와 `apps/web/src/components/UpdateSettings.tsx`의 파일 기반 요청/상태 전달은 재사용할 수 있다.
- 앱에는 Docker socket을 주지 않고 호스트 도구가 재시작을 담당하는 현재 경계는 유지한다.

## 릴리스 정책

| 항목 | 정식 | 베타 | 개발 빌드 |
| --- | --- | --- | --- |
| 버전 예시 | v1.2.0 | v1.3.0-beta.1 | sha-커밋 |
| GitHub 표기 | Release | Pre-release | 정식 피드에 미노출 |
| 대상 | 기본값, 일반 사용자 | 먼저 사용해 볼 사용자 | 개발자 |
| 후보 선택 | 지원 가능한 정식 버전 | 정식+베타 중 지원 가능한 가장 높은 버전 | Git/수동 관리 |

- SemVer로 비교한다. 날짜나 문자열 정렬, `latest` 하나로 후보를 고르지 않는다. 예시 버전은 첫 공개 버전 번호를 확정한 것이 아니다.
- 정식 승격은 검증된 같은 커밋에서 수행한다. 빌드에 버전이 내장되므로 재빌드할 경우 최종 정식 산출물도 확인한다. 서로 다른 버전을 같은 산출물이라고 주장하지 않는다.
- 공개한 버전과 그 manifest는 덮어쓰지 않는다. 결함은 다음 patch/beta 릴리스로 수정한다.
- 베타 채널도 대응 정식 버전을 받는다: v1.3.0-beta.2 → v1.3.0. 채널을 정식으로 바꿨는데 현재 베타보다 낮은 정식만 있으면 유지하고 다음 정식을 기다린다.
- 자동 다운그레이드는 금지한다. 이전 버전 복구는 별도 작업이며 DB 호환성 검사를 거친다.
- main 자동 빌드는 edge 또는 sha 태그만 사용한다. latest/stable은 완성된 정식 릴리스만 가리키고 beta는 완성된 베타를 가리킨다. 업데이터 실행은 이 가변 별칭 대신 고정 digest를 사용한다.
- 채널 전환은 즉시 설치를 뜻하지 않는다. 새 채널 후보를 확인한 뒤 기존 자동 적용 정책을 따른다. 베타 위험 안내는 채널 선택 시 짧게 한 번 제공한다.

## 배포 단위와 설치 파일

각 GitHub 릴리스에는 다음을 제공한다.

1. 변경 사항·호환성·필요한 조치·알려진 문제를 담은 릴리스 노트.
2. `release.json`: 릴리스 전체를 식별하는 작은 선언형 manifest.
3. `moa-install.tar.gz`: compose 템플릿, env 예시, 설치/업데이트 도구, 필요한 배포 설정 파일, 라이선스. 소스 전체나 사용자 데이터는 포함하지 않는다.
4. 설치 파일의 체크섬과 서명, 이미지/manifest의 출처 검증 자료.

manifest v1 필드 제안:

- schemaVersion, version, revision, channel, publishedAt, releaseNotesUrl.
- services: moa/auth/apk/connector/source-browser 각각의 저장소, 고정 digest, 지원 platform, 필수/선택 여부.
- minimumUpdaterVersion, minimumComposeVersion, 지원하는 현재 설치 버전 범위.
- deploymentBundle: 파일명, digest, 크기, 설치 형식 버전.
- migration: 데이터 스키마 버전, 구버전 실행 가능 범위, 자동 복구 가능 여부.
- updater artifact: 버전과 고정 파일명/digest. 임의 셸 명령·임의 다운로드 URL·사용자 지정 hook은 허용하지 않는다.

서비스 이미지 버전이 모두 같을 필요는 없지만, 하나의 manifest가 호환되는 정확한 조합을 지정한다. 선택 기능이 꺼져 있으면 해당 이미지를 받거나 실행하지 않는다. 브라우저 서비스의 현재 amd64 제한은 manifest에 명시하고 arm64 설치에서는 자동 활성화하지 않는다. 앱의 arm64 지원과 혼동하지 않는다.

일반 설치는 Git checkout이 아닌 전용 설치 폴더를 사용한다. updater가 관리하는 배포 파일과 사용자의 `.env`/override/volume을 분리한다. 기존 사용자 compose 파일을 덮어쓰지 않는다. 변경된 포트·장치·볼륨·네트워크가 없는지 해석된 compose 설정을 비교하고, 지원 범위를 벗어난 차이는 수동 이관을 안내한다.

## 발행 파이프라인

1. maintainer가 버전 태그를 지정한다. 형식·채널·소스 커밋·지원 아키텍처를 검사한다.
2. 관련 검사와 이미지 빌드를 진행하고 버전/커밋 OCI label을 넣는다.
3. 필수 이미지·지원한다고 선언한 선택 이미지·설치 파일·업데이터 산출물을 검증한다.
4. 실제 digest로 manifest를 만들고 서명한다. 체크섬만으로 게시자 신원을 검증한다고 간주하지 않는다.
5. 모든 필수 산출물이 준비된 뒤 draft를 Release/Pre-release로 공개한다. 실패한 중간 빌드는 업데이트 후보가 되지 않는다.
6. stable/latest/beta 별칭을 갱신한다. 일부 별칭 갱신 실패가 manifest 기반 설치 조합을 바꾸지는 않는다.

릴리스 목록은 GitHub API를 사용한다. 정식/베타 선별은 published 릴리스와 SemVer/manifest를 함께 확인한다. beta 목록은 latest API에 의존하지 않는다. 페이지 조회에 상한을 두고, 지원되는 새 버전을 찾지 못했다면 무조건 최신이라고 표시하지 않는다.

manifest/업데이터 진위 검증은 고정된 프로젝트 신뢰키로 수행하는 방식을 우선한다. 키는 런처에 포함하며 키 교체는 기존 키로 검증된 업데이트로 전달한다. CI 서명 비밀은 배포 환경에 제한한다. 모든 HTTP와 아카이브 입력의 크기·시간·경로·대상 저장소를 제한한다.

## 호스트 업데이터

설치 모드를 명시적으로 분리한다.

- `release`: Git 존재와 무관하게 릴리스 manifest 및 고정 이미지를 사용. 신규 Docker 설치의 기본값.
- `source`: 현재 추적 브랜치 기반 갱신/빌드. 기존 개발 설치용, 무인 자동 적용 기본 비활성.
- 이전 `auto|git|docker` 옵션은 이관 기간에 호환 처리하고 최종 선택된 모드를 명확히 표시한다. 기존 설치를 조용히 release로 바꾸지 않는다.

호스트 도구는 버전별 디렉터리와 작은 고정 런처로 나눈다. 새 도구를 검증·설치하고 작업이 없을 때 current 포인터를 원자적으로 교체한다. 부팅/헬스 handshake 실패 시 이전 도구로 복구한다. 업데이트 도구가 자기 실행 파일을 실행 중 덮어쓰지 않는다. 앱과 도구의 프로토콜 범위를 manifest에 명시하며, 앱 업그레이드 전에 필요한 도구 업그레이드를 완료한다. 호스트 Node 등 시스템 런타임은 몰래 설치/갱신하지 않는다. 최초 설치 도우미가 필요 버전과 도구 서비스 등록을 처리한다.

기존 systemd 사용자 서비스와 파일 기반 통신을 재사용한다. 상태에는 도구 버전/연결, 설치 버전, 대상 버전, 채널, 다음 확인/적용 시각, 단계, 복구 여부를 담는다. 웹앱 요청은 제한된 구조의 의도만 전달하며 명령/경로를 전달하지 않는다.

## 업데이트 확인 및 자동 적용

추천 기본값:

| 설정 | 기본값 |
| --- | --- |
| 채널 | 정식 |
| 자동 확인 | 켜짐, 6시간마다 ±10% 분산 |
| 자동 적용 | 꺼짐 |
| 자동 적용 시간 | 사용자가 켤 때 서버 시간대와 시간 구간 선택 |
| 재생/중요 작업 중 | 적용 보류 |
| 구버전 보존 | 최근 성공 2개, 진행 중 복구용 파일은 삭제 금지 |

- 확인은 작은 릴리스 metadata/manifest만 가져온다. ETag/조건부 요청, 오류 backoff, rate-limit 응답을 처리한다. 확인 중 대용량 이미지 pull은 하지 않는다.
- 수동 확인, 예약 확인, 자동 적용이 동시에 실행되지 않도록 하나의 작업 큐/설치 lock을 사용한다.
- 체크 당시 대상 version+manifest digest를 작업에 고정한다. 적용 중 새 릴리스가 나와도 대상을 바꾸지 않는다.
- 자동 적용은 명시적으로 켠 설치만 수행한다. 예약 시각이 지나도 busy면 다음 기회를 기다리고 이유를 표시한다. 시간이 지나면 강제로 재생을 끊는 기본 동작은 없다.
- 자동 적용 전 서버에서 재생 세션과 scan/translation/backup 등 중단 위험 작업을 확인한다. heartbeat가 없거나 상태를 확신할 수 없으면 자동 적용하지 않는다.
- 적용 직전 maintenance lease로 새 장기 작업/재생 시작을 잠시 제한해 확인 직후 새 재생이 시작되는 경합을 막는다. 실패/취소 시 lease가 만료되며 자동 해제된다.
- 수동 적용에서 busy일 때만 중단 가능성을 표시한다. 확인/다운로드 단계는 서비스를 계속 제공한다.
- UI 연결이 끊겨도 호스트 작업은 계속된다. 완료/복구 결과와 요약 이력을 재연결 후 표시한다.

## 적용과 복구 상태 흐름

`확인 → 사용 가능 → 다운로드 → 사전 확인 → 작업 대기 → 백업 → 적용 → 상태 확인 → 완료`

실패 단계에 따라 `기존 버전 유지`, `이전 버전 복구 중`, `복구 완료`, `수동 복구 필요`로 나눈다. 실패 버전은 자동 재시도를 억제하고 다음 버전 또는 사용자의 재시도 요청을 기다린다.

1. 지원 버전/platform, 디스크 여유, compose/업데이터 버전, 활성 서비스 조합을 확인한다.
2. 모든 필요한 digest를 먼저 pull하고 진위와 존재를 검증한다. 실패하면 기존 컨테이너는 계속 실행한다.
3. maintenance lease 및 설치 lock을 확보하고 DB/설정의 일관된 백업을 만든다. 앱 DB와 인증 DB 등 실제 구성의 데이터 저장소를 모두 열거한다. WAL 파일을 단순 복사하지 않는다. 필요하면 짧게 쓰기 서비스를 멈춘다. 비밀을 포함하는 백업은 소유자 전용 로컬 경로에만 둔다.
4. 현재 image digest·배포 설정·백업 위치·DB 상태·진행 단계를 호스트 journal에 기록한다. journal과 포인터는 원자적으로 갱신한다.
5. updater가 관리하는 버전별 compose 파일로 전환하고 해당 서비스만 재생성한다. 새 버전이 healthy여도 앱 readiness/migration 완료와 필요한 서비스 간 연결을 추가 확인한다. gateway upstream 변경도 반영한다.
6. 성공하면 current 버전을 확정하고 lease 해제, 이전 성공 버전을 보존한다.
7. 이미지 교체 실패/health 실패 시 구버전 DB 호환성을 확인한다. 가능하면 이미지 조합만 복구한다. 불가능하면 새 앱의 사용자 쓰기를 받기 전에 백업 복구가 가능한 릴리스에 한해 데이터와 이미지를 함께 복구한다.
8. 되돌릴 수 없는 migration은 기본 자동 적용 대상에서 제외한다. 사용자가 이미 새 버전에서 쓴 데이터에 대해 자동으로 예전 DB를 덮어쓰지 않는다.
9. 도구/호스트가 중간에 재시작돼도 journal로 실제 컨테이너·DB 상태를 대조하고 이어서 완료/복구한다. 단순 PID 파일만으로 작업 상태를 판단하지 않는다.

## 관리자 화면

기존 설정의 업데이트 패널을 확장한다. 일반 사용자에게 Git 커밋·digest·호스트 명령을 주 정보로 노출하지 않는다.

- 현재 버전 `v1.2.0`, 새 버전 `v1.2.1`, 채널 `정식 / 베타`.
- 마지막 확인, 변경 사항, `업데이트 확인`, `지금 업데이트`.
- 자동 확인/자동 적용, 적용 시간대·시간 구간, `재생 중에는 미룹니다` 짧은 안내.
- 적용 중에는 현재 단계와 재연결 안내. 버전 제외/보류·실패·복구 이유는 쉬운 문구로 표시.
- 상세 영역에 이미지/커밋·도구 버전·지원 불일치·설치 이력. 모호한 현재버전 unknown 대신 `사용자 빌드`를 별도 표시.
- 정상 연결된 설치에서는 '호스트 도구' 설정 안내를 숨긴다. 연결되지 않았을 때만 설치 안내를 보여준다.
- UI 구현은 사용자 지정 UI 담당 프로필에 맡긴다. 계획 작성 단계에서는 화면 코드를 수정하지 않았으며, 이후 구현 상태는 아래에 기록한다.

## 기존 설치 이관

1. 현재 설치의 프로젝트명, volume, `.env`, overrides, 이미지, 활성 기능, 도구 경로를 읽어 이관 미리보기를 만든다.
2. 기존 source 설치/로컬 변경을 감지해 보존한다. 신규 릴리스가 현재 필요한 기능을 포함하고 지원하는지 확인하기 전에는 자동 전환하지 않는다.
3. 관리 배포 폴더를 따로 만들고 기존 데이터 경로를 참조한다. 개발 Git 작업트리는 변경하지 않는다.
4. 한 번 수동으로 선택한 버전으로 이관하고 health·재생·선택 서비스·재부팅 후 updater 연결을 확인한다.
5. 이후 확인/자동 적용을 제공한다. 사용자 확장·플러그인·개별 설정을 릴리스 파일로 덮어쓰지 않는다.

비공개 확장/사이트별 코드·식별자·fixture·인증자료·사용자 DB는 공개 릴리스, 이미지, CI 산출물에 절대 넣지 않는다. 공개 변경에는 범용 호스트 기능만 포함한다.

## 구현 순서와 완료 조건

1. **배포 계약/CI**: manifest schema·버전 정책·아키텍처·서명·설치 묶음, 브라우저 이미지 포함. 불완전 빌드가 후보로 공개되지 않아야 한다.
2. **release 확인/수동 적용**: 명시적 설치 모드, 정식/베타 후보 선정, version 표시, digest별 이미지 다운로드, 현재 파일 통신 확장. check가 이미지를 받지 않는지 확인한다.
3. **복구와 도구 갱신**: journal, 일관 백업, schema 호환성, self-update launcher, 재시작 복구. 손상/중단된 설치의 복구 경로까지 만든 후 자동 적용을 연다.
4. **예약과 UI**: 주기적 확인·수동/자동 작업 단일화·busy/maintenance·시간대·이력. 기본 자동 적용 off.
5. **베타 운영→정식**: 개인 환경에서 한 번 실제 이관·업데이트·복구를 확인한 뒤 초기 공개 베타를 발행한다. 베타에서 충분히 운영한 후 정식으로 승격한다.

필수 테스트를 각 단계 완료 시 묶어서 실행한다: SemVer/채널/플랫폼 선정, 위조·손상manifest, 부분발행, 기존override 보존, 중복작업, 취소/재시작journal, busy 경합, 실패health/DB복구, 구도구 호환. fake registry/compose로 대부분 확인하고 대표적인 실제 업데이트/복구 1회로 연결을 확인한다. 제품 구현자는 직접 검토하며 반복적 대규모 실험은 하지 않는다.

## 초기 범위에서 제외

별도 중앙 업데이트 서버, Canary 비율 배포, 강제 베타 참여, 자동 major downgrade, 사용자 compose 임의 수정, 비공개 확장 자동 배포, Git 개발 브랜치 자동 병합, Docker socket을 웹앱에 부여하는 방식, 모든 호스트 OS에 대한 installer는 제외한다.

## 참고한 공식 문서

- GitHub Releases API: https://docs.github.com/en/rest/releases/releases — published/draft/prerelease 및 asset 조회.

## 구현 상태 (feat/release-updater)

- 정식/베타 후보, 서명·digest 검증, 명시적 release 모드, 자동 확인/시간 구간/자동 적용 opt-in, 관리자 UI, 파일 IPC와 maintenance lease를 구현했다.
- 고정 이미지 조합, 실제 실행 이미지 확인, 쓰기 서비스 정지 후 앱/인증/APK/connector `/data` 백업, health 확인, 호환 이미지 복구와 journal 재시작 복구를 구현했다. 최근 두 백업을 성공 뒤 보존 정리한다.
- 새 도구는 서명된 파일 묶음의 고정 allowlist로 설치하고 protocol probe 후 포인터를 바꾼다. 시작 실패 시 이전 도구로 복귀한다. bootstrap 신뢰키 확인, 고정 런처 자체 갱신과 키 회전은 관리자 작업이다.
- 첫 구현은 **같은 schemaEpoch + rollbackSafe 선언** 범위로 인앱 적용을 제한했다. 비가역 migration 및 새 Compose 구조는 수동 이관 대상으로 차단한다. 자동 DB snapshot 복원은 제공하지 않는다. 사용자 쓰기를 덮어쓸 위험을 피하기 위한 범위 제한이다.
- 설치기는 fresh install, read-only preview, 정확히 같은 release digest로 실행 중인 설치의 adopt를 제공한다. 사용자 빌드를 release로 자동 교체하지 않는다. 서비스 등록 명령은 생성된 systemd unit을 확인한 뒤 한 번 실행한다.
- 공개 artifact 생성/서명, 전체 이미지 완료 후 draft 공개, stable/beta/edge 정책의 CI를 구현했다. 서명키, 첫 버전과 migration 선언, GitHub environment 설정 및 실제 발행은 아직 하지 않았다.
- 합성 host/API tests, UI smoke, 실제 격리 Docker의 정상 업데이트와 의도적 health 실패 후 복구·데이터 보존을 확인했다. 실제 공개 registry 다중 플랫폼 빌드/발행과 개인 운영 이관은 후속 단계다.
