# 외부 확장과 호환되는 작품·회차 식별 개선 계획

작성: 2026-10-09. 아래는 구현 전 합의한 계획이다. 같은 날짜에 PR #10 브랜치에 구현했으며 운영에는 미배포다. 현재 동작과 제한은 [SOURCE-IDENTITY.md](SOURCE-IDENTITY.md)를 따른다. 검증은 합성 확장·임시 DB 중심이며 실제 외부 사이트 전체의 동작 보장을 의미하지 않는다.

## 목표와 판단

같은 설치 소스의 접속 주소가 변경되어도 작품·회차의 내부 ID, 프로필별 진행률, 즐겨찾기, 자막 연결을 유지한다. 기존 Mangayomi JS 및 Aniyomi APK를 수정 없이 계속 사용할 수 있어야 한다. 특정 저장소나 사이트에 의존하거나 사용자가 확장마다 주소 규칙을 설정하는 방식은 사용하지 않는다.

모든 사이트의 개편을 자동으로 이해할 수 있다는 보장은 하지 않는다. 주소·경로·제목·회차 체계가 동시에 바뀌고 안정적인 식별 정보도 없다면 동일성은 결정할 수 없다. 이때 기존 데이터를 보존하고 확장의 원래 동작을 유지하는 것이 호환성 기준이다.

현 PR은 숫자 도메인 이동에는 유효하지만 범용 설계로는 부족하다. hostname의 숫자 제거를 동일성의 핵심 조건으로 삼고, 가장 큰 숫자를 최신 접속 주소로 취급한다. TLD/이름 변경과 이전 주소로의 복귀를 표현하지 못하며, 주소 선택과 기록 식별을 혼합한다. 관련 20개 테스트 통과는 이 범위의 동작 증거이지 모든 외부 확장에 대한 보장이 아니다.

## 검토한 계약과 실제 코드

- `packages/extensions/src/types.ts`: 외부 작품에는 `link`, 회차에는 `url`이 있다. 보편적인 영구 ID 필드는 없다. JS의 해당 반환 계약은 유지한다.
- `packages/extensions/src/bootstrap.ts`: `getDetail(workUrl)`, `getVideoList(episodeUrl)`에 식별자를 그대로 전달한다. 상대 경로나 임의 문자열을 임의의 절대 URL로 변환하면 기존 확장이 깨질 수 있다.
- 공개 Mangayomi 영상 확장 표본에서 상대 경로 반환, 절대 URL 반환, 확장 내부 도메인 조회, 별도 스트림 호스트를 확인했다. 이는 코드 검토 표본이며 모든 공개 확장의 실제 재생 검증은 아니다.
- `apps/server/src/apk-bridge.ts`: APK도 같은 호스트 모델로 변환되지만 패키지 하나에 여러 소스가 있고, 실제 설치된 descriptor의 `baseUrl`이 인덱스와 다를 수 있다. 목록 인덱스만 갱신한 것을 설치 완료로 취급하지 않는다.
- `apps/server/src/sources.ts`: `entry`와 `installed_entry`를 구별하며 설치·롤백·설정 변경 시 캐시를 무효화한다. 이 경계에 주소 변경 관찰을 연결한다.
- 현재 DB는 이미 내부 ID와 접속 URL을 별도 필드에 저장한다. 문제는 새 응답을 기존 ID와 연결하는 규칙이다. 전체 DB 구조나 플레이어를 재작성할 필요는 없다.
- Mangayomi의 확인한 구현은 독립 DB ID를 유지하고, 회차 동기화에서 도메인을 제외한 경로·query·fragment 및 회차 인식 결과를 비교한다. 시즌·소수 회차·번역 그룹 구분도 고려한다. 작품과 회차의 모든 매칭을 동일한 규칙으로 처리한다고 해석하지 않는다.

## 1. 내부 ID와 외부 주소의 역할 분리

- 기존 `media.id`, `episodes.id`, 설치 소스 ID는 하나도 다시 만들지 않는다. 해시 모양이어도 생성 후에는 불변 ID로 사용한다.
- 과거 URL과 현재 URL을 모두 같은 내부 ID에 연결할 수 있도록 주소 별칭을 저장한다. 옛 URL 재등장과 캐시 응답이 새로운 작품을 만들지 않게 한다.
- 신규 항목은 별칭/동일성 조회에 실패한 뒤에만 ID를 배정한다. 이번 변경에서는 기존 해시 형식의 최초 ID 생성도 유지한다. 생성 후에는 URL과 분리된 불변 ID로 취급하며, 새 URL로 해시를 다시 계산해 기존 기록을 교체하지 않는다.
- UUID/난수 ID로 형식을 바꾸는 것만으로 동일 작품 판단이 해결되는 것은 아니다. 핵심은 매칭과 별칭 보존이다. 전체 ID 형식 변경은 이번 범위에서 제외한다.
- 작품 매칭 범위는 현재 설치 소스 ID 내부, 회차 매칭 범위는 현재 작품 ID 내부로 제한한다. 저장소·언어·APK sibling source는 기존대로 격리한다.
- 별칭은 중복을 표현할 수 있어야 한다. 하나의 URL에 기존 ID가 둘 있으면 `REPLACE`로 덮거나 임의 선택하지 않는다. 이미 알려진 ID로 상세를 열었을 때는 그 ID를 유지한다.

저장 항목은 기존 테이블에 더하는 방식으로 구성한다. 작품/회차별 주소 별칭과 소스별 주소 변경 기록을 저장하고, 검색용 인덱스를 둔다. URL 원문과 비교용 키를 구분한다. 공개 API와 확장 입력에 비교용 키를 전달하지 않는다.

## 2. 주소 변경 관찰: 숫자 크기 대신 근거와 설치 상태

자동 관찰의 우선순위:

1. 같은 소스의 정상 설치 완료에서 `installed_entry.baseUrl`이 바뀐 경우 이전·새 기본 주소의 관계를 기록한다. 숫자 변경, TLD 변경, 이름 변경을 모두 처리한다. 단순 저장소 새로고침은 후보 정보일 뿐 실제 접속 주소를 바꾸지 않는다.
2. 특정 작품 ID의 상세 요청이 성공하고 같은 경로의 새 작품 URL을 반환하면 그 작품에 대한 주소 별칭을 기록한다. 이것만으로 다른 작품·외부 영상 호스트 전체를 이전시키지 않는다.
3. 확장이 목록 등에서 숫자만 다른 같은 호스트 계열을 반환하면 기존 숫자 이동 지원을 유지한다. 숫자는 후보의 계열 판별에만 사용한다. 숫자가 크다는 이유로 전역 현재 주소를 바꾸지 않는다. 실제 항목 대응과 성공한 요청을 기준으로 채택한다.
4. 확장이 자체 주소 resolver를 가지고 상대 경로나 고정 식별자를 반환하면 해당 계약을 그대로 사용한다. 호스트가 resolver를 다시 구현하지 않는다.

일반 HTTP의 리다이렉트 전체를 수집해 소스 주소로 승격하는 기능은 초기 범위에서 제외한다. 광고·로그인·API·CDN 리다이렉트를 사이트 이전으로 오인할 수 있고 APK/브라우저까지 계측 범위를 넓혀야 한다. 향후 필요할 때 특정 탐색 요청에 귀속된 결과만 검토한다.

한 소스가 동시에 여러 origin을 반환하면 이를 별개 주소 공간으로 유지한다. 확장 기본 주소의 이전은 그 기본 주소에 속한 항목만 연결하며, 무관한 호스트에는 전파하지 않는다. `api.example.test`가 기본 주소인 확장의 모든 콘텐츠 호스트를 API 주소로 바꾸지 않는다.

기본 URL에 `/site-a/` 같은 경로가 있으면 그것도 주소 공간의 일부다. 초기 버전은 origin만 바뀌고 base path는 유지되는 이전을 지원한다. base path까지 바뀌면 prefix를 추측하여 잘라 붙이지 않는다.

확장 롤백은 숫자의 대소가 아니라 실제 복원된 설치 상태를 따른다. 이전 설치에서 얻은 모든 origin 관계를 삭제하지는 않되, 새 요청에 사용할 활성 후보는 복원된 설치 상태에서 선택한다. 오래된 목록/캐시 응답은 활성 주소를 다시 과거로 되돌리지 못한다.

## 3. 매칭 규칙과 원문 보존

순서:

1. 이미 알고 있는 작품/회차 ID로 요청한 결과는 해당 ID에 갱신한다.
2. 같은 범위에서 저장된 URL/식별자 원문과 정확히 일치하는 별칭을 찾는다.
3. 확인된 동일 주소 공간에서 경로·query·fragment가 일치하는 후보를 찾는다.
4. 후보가 하나일 때만 재사용하고, 후보가 없으면 새 ID를 배정한다. 여러 개면 자동 병합하지 않는다.

| 외부 확장의 식별자 | 처리 |
| --- | --- |
| 절대 HTTP(S) URL | 정확한 별칭 우선. 확인된 사이트 이전 관계 안에서만 origin 제외 비교 |
| `/work/1`, 상대 경로 | 입력 원문 보존. 기본 주소 변경만으로 새 ID가 생기지 않게 함 |
| 절대↔상대 표현 전환 | 확인된 기본 주소 공간 안에서 동일 경로가 유일할 때 연결 |
| JSON, 특수 문자열, 비 HTTP scheme | 불투명 식별자로 원문 비교. 내부 URL·숫자를 파싱하거나 변경하지 않음 |
| query/hash로 회차를 지정 | query/hash 보존. 파라미터 삭제·정렬·디코딩·회차 숫자 추측 금지 |
| 여러 호스트의 동일 경로 | 이전 관계가 없으면 구분. 같은 `/watch/1`이라는 이유로 합치지 않음 |
| 제목만 같거나 시즌·회차번호만 같음 | 초기 버전의 자동 병합 근거로 사용하지 않음 |

오래된 불투명 식별자가 새 JSON 구조로 바뀌는 경우, 경로 자체의 개편, 저장소/확장 ID 변경은 자동 이전 대상이 아니다. 기존 기록은 그대로 남긴다. Mangayomi가 제공하는 회차 이름 인식까지 이번 변경에 복제하지 않는다.

## 4. 홈 직접 이어보기와 확장 호출

- 이미 알고 있는 현재 주소/별칭을 DB에서 선택한다. 홈에서 재생할 때마다 목록·검색·상세를 강제 요청하지 않는다.
- 활성 설치와 대응이 확인된 이전 관계가 있으면 해당 절대 URL의 origin만 바꿔 호출할 수 있다. 상대·불투명 식별자는 그대로 전달한다.
- 자동으로 바꾼 식별자가 실패하거나 영상 결과가 비면 원래 식별자로 한 번만 복귀한다. 설치/결제 등 다른 작업은 재시도 대상이 아니다. 취소·종료 시에는 추가 호출하지 않는다.
- 새 주소가 실제로 성공하기 전에는 원본 URL을 폐기하지 않는다. 같은 설치 상태에서 실패한 후보는 짧게 기억해 매 재생마다 불필요한 재시도를 반복하지 않는다.
- 영상 파일·HLS·자막·포스터·쿠키·Referer는 탐색용 작품/회차 URL과 별개다. 이 주소들을 일괄 치환하지 않는다. 실제 미디어 요청은 확장이 반환한 값과 기존 네트워크 정책을 따른다.
- APK 추출의 임대 자원은 실패·재시도 경로에서도 해제한다. 기존 source/package queue를 우회하거나 중첩 잠금을 만들지 않는다.
- 성공한 응답의 주소/별칭 갱신은 설치 세대와 작업의 유효성을 확인한 뒤 트랜잭션으로 적용한다. 설치·설정 변경·롤백·삭제 전에 시작한 응답이 나중에 최신 상태를 덮어쓰지 않게 한다.

## 5. 호환성과 데이터 이관

- 외부 JS/API, APK 인터페이스, 확장 설정 UI는 변경하지 않는다. 신규 `stableId` 필드나 MOA 전용 확장 작성이 필수인 설계를 도입하지 않는다.
- 전역 테스트용 도메인 외에 사이트별 식별자나 예외표를 공용 코드에 넣지 않는다.
- 기존 DB에서 ID를 보존한 채 주소 별칭만 backfill한다. 여러 프로필의 진행률, 기록, 즐겨찾기, 저장 자막, 번역·스킵 정보와 클라이언트 링크는 그대로 유지한다.
- backfill은 버전 표시와 트랜잭션으로 한 번 수행하고 재실행 가능하게 한다. 서버가 시작될 때마다 모든 주소를 재작성하지 않는다.
- 구 PR #10 테이블이 있는 개발 DB도 고려한다. 단순 숫자 family 기록을 임의 도메인 이전의 검증 근거로 승격하지 않는다. 실제 URL/설치 정보에서 다시 구성한다.
- 캐시 payload에 든 내부 ID는 유지하며, 과거 URL 별칭이 재등장해도 현재 주소 선택과는 분리한다.
- 삭제/재설치 시 해당 소스의 별칭·주소 관계도 함께 정리한다. source_entries 행 자체를 남기는 현재 uninstall 동작에서는 FK cascade만 믿지 않는다.
- 새 테이블을 추가했다고 구버전 실행까지 안전한 것은 아니다. 구버전은 새 주소를 기존 ID에 연결한 별칭을 조회하지 못해 다시 탐색할 때 중복 항목을 만들 수 있다. 검증 전 릴리스의 `rollbackSafe`를 선언하지 않는다. 배포 실패 직후 복구는 쓰기 전 DB 백업과 이미지 쌍으로만 처리하며 이후 사용자 기록을 임의로 덮지 않는다.

## 6. 최소 검증 묶음

외부 사이트 요청을 반복하지 않고 합성 확장/임시 DB 중심으로 한 번 묶어 확인한다.

1. 숫자 증가·감소, TLD/이름 변경과 확장 롤백: 동일 ID와 기존 진행 위치 유지.
2. 상대 경로, 절대 URL, JSON/문자열, query/hash, base path: 원문 전달과 별도 회차 구분 유지.
3. 집계 소스의 같은 경로/다른 호스트, 같은 제목/다른 작품, 언어·저장소·APK sibling source: 잘못된 병합 없음.
4. 기존 DB 재시작/backfill, 과거 주소 재등장, 중복 기존 기록, 두 프로필·즐겨찾기·자막 보존.
5. 홈 직접 재생: 불필요한 목록/상세 요청 없음, 시작 위치 유지, 실패 fallback 제한, 취소와 APK 임대 해제.
6. 설치/설정 변경/롤백과 진행 중 응답의 경합, 오래된 캐시가 주소를 되돌리지 않음, 삭제 후 상태 잔류 없음.
7. 기존 Mangayomi/APK 회귀 테스트. 실제 외부 JS 표본은 수정 없이 MOA QuickJS에서 실행하고 네트워크를 고정 fixture로 대체하여 입력·출력 계약 확인. APK 브리지는 기존 패키지 fixture로 경로 확인.
8. 서버 타입 검사와 구버전 호환성 확인. 실제 사이트 확인은 필요할 때 대표 사례만 수행하며 이를 모든 확장 성공으로 표현하지 않는다.

## 구현 순서와 완료 기준

1. PR #10을 보류한 채 내부 ID/주소 별칭 모델과 migration을 구현한다. 기존 기록을 먼저 보존한다.
2. 설치·롤백의 주소 변경 이력과 일반 매칭을 연결한다. 숫자 이동을 지원하되 숫자 최대값 선택은 제거한다.
3. 홈 직접 이어보기의 주소 선택, 제한된 fallback, 취소/동시성 처리를 연결한다.
4. 위 검증 묶음을 완료하고 PR #10의 제목·본문·설계 문서를 최종 범위로 갱신한다.
5. 리뷰 후 다음 베타에 반영한다. 기존 사용자 DB가 유지되는지 확인하기 전 정식/자동 배포로 진행하지 않는다.

완료 기준: 외부 확장 수정·사용자별 설정 없이 기존 소스가 작동하며, 확인된 숫자/TLD/이름 변경에서 ID와 기록이 유지된다. 근거 없는 변경은 기존 경로와 기록을 보존한다. 모든 외부 사이트 개편을 자동 복구한다고 안내하지 않는다.
